# Multi-tenant security model (v0.3.0)

**Trust boundary:** Host `HTTP_HOST` is validated; multi-tenant host resolution looks up an exact configured hostname in `tenant_domains` for an active `tenants` row. The control domain is a separate, explicitly trusted host; it never resolves to a tenant. Neither missing/disabled tenants nor central routes on tenant hosts fall back to another tenant.

**Request lifecycle:** `Kernel` clears tenant request context before/after dispatch. Tenant route handlers must use `ContextStore::current()->requireTenantId()`, `TenantAccess::guard(...)`, or tenant-scoped repositories. Avoid static/global tenant state and tenant ID query parameters. Background jobs must set explicit context and authorization for each company, then clear context before processing the next job.

**Global versus tenant identity:** `users` is a global identity store; each company's authorization comes from `tenant_memberships`. Global admin is based on global user groups/permissions; a tenant owner is never implicitly a platform admin. `TenantAccess::membership()` uses a fresh DB query and checks both user and tenant `active` status to honor revocation quickly.

**Owner safety:** Tenant `owner` can manage all roles; admin can manage only editor/viewer members. Membership mutations check the authenticated actor and current context, lock the tenant row using `FOR UPDATE`, then check authorization and preserve at least one owner.

**Invites:** Issue requires authenticated central tenant-manager permission or a matching tenant membership with sufficient role. A SHA-256 digest, not the raw 256-bit token, is stored; `expires_at` uses UTC, token consumption is transactional with `FOR UPDATE`, links work only on the same tenant domain and are rejected after acceptance. Existing users supply their existing password, while new users create an Argon2id password. The link itself is a bearer secret — it must be delivered only to the intended person. **Manual delivery does not independently verify email ownership.** Implement verified-email delivery before allowing self-service public onboarding.

**Session security:** Host-only cookies, secure cookie naming on TLS, HTTP-only cookies, `SameSite=Lax`, session ID rotation on login/logout, CSRF tokens for write routes, throttled login and invite accept requests. Keep `SESSION_SECURE=true` and correct HTTPS termination in production; `TRUSTED_HOSTS` must not be wildcarded for the central host. Never trust client-supplied `X-Forwarded-*` headers unless you implement an explicit trusted-proxy list.

**Headers and logging:** Tenant/session/invitation pages use private no-store caching. Invitation pages explicitly set `Referrer-Policy: no-referrer`; `deploy/nginx.conf.example` includes an `/invite/` access-log exclusion. Other reverse proxies, CDN request logs, browser history, APM, error trackers and support recordings may still capture bearer URL tokens — scrub paths at every layer. Never send invitation URLs to analytics providers. Enable TLS, backups, monitoring and firewall protection in production.

**Data access:** `TenantRecords`/`TenantCache` are tenant-scoped API helpers; raw `Database` SQL, legacy modules and all custom integrations can still perform unscoped queries. A shared MySQL schema is not automatic row-level security. Audit SQL paths, API handlers, files, scheduled workers, cache keys, WebSocket channels, media downloads and exports for tenant boundaries. Do not claim production-grade tenant isolation until all those paths and full integration tests are reviewed.

**Test gate:** Before production, validate schema migrations, concurrent/replayed invitations, suspended company routes, login/CSRF, last-owner edge cases, role escalation attempts, IDOR across tenants, 2+ tenant media and caching, invalid proxy hosts, secure cookies, SSL and rate-limit behavior under load. The MySQL integration script is available, but has not been executed in this authoring environment.
